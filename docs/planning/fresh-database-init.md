# Explicit fresh-database initialization (unreleased app contract)

This is a separate, operator-invoked path for an **already empty** PostgreSQL database. It does not create, drop, truncate or reset a database and never adopts an existing schema. It is not a flag on `bootstrap-db`, `migrate`, or the predecessor-bound disposable replacement. Nothing in this document authorizes a production operation.

- Run the *candidate* `server fresh-init-db --confirm-empty` only with a bootstrap-superuser connection to the named target. For a stamped candidate, `APP_VERSION` and `GIT_SHA` must match the binary release contract and its fixed database name. The command rejects a missing flag, an unknown database, any preexisting object dependent on `public` (including function-only databases), any non-system schema or a public extension before it changes roles or schema. Missing app, migration, media-cleanup or data-retention credentials also fail before DDL. It uses the same environment/config role names as `bootstrap-db`: `APP_DB_USER`/`APP_DB_PASSWORD`, `MIGRATION_DB_USER`/`MIGRATION_DB_PASSWORD`, `MEDIA_CLEANUP_DB_USER`/`MEDIA_CLEANUP_DB_PASSWORD`, `DATA_RETENTION_DB_USER`/`DATA_RETENTION_DB_PASSWORD`, plus the bootstrap `DATABASE_URL` (or existing `BootstrapDatabaseURL` config). The host owner supplies those values without exposing them in logs; this branch does not edit host configuration.
- The app command installs the existing role/ACL bootstrap, applies the embedded fresh baseline plus forward migrations and hardening under the migration role, checks the real schema and 77-entry ledger, then records a private superuser-owned, migration-read-only fresh-init receipt bound to database, stamped identity and inventory digest. The receipt is NOT the predecessor-reset completion. A failed partial run on a now nonempty DB refuses retry and requires separately reviewed recovery; never automatically wipe or reinterpret it as v1.25.9.
- Existing stamped `bootstrap-db` and `migrate` accept only a valid private receipt whose schema and table are both owned by a PostgreSQL superuser, *and* the exact actual ledger/schema; migration-role-owned matching rows do not qualify. Otherwise they retain their pre-existing disposable predecessor/completion checks. An invalid present fresh receipt is a hard stop, not fallback. The generic host release sequence still needs SRE integration; do not run it against an empty DB assuming it invokes this command.
- The release Dockerfile builds the unchanged `cmd/admin` into `/app/admin` alongside `/app/mycfc`, stamped with the **same** immutable `RELEASE_VERSION`/`GIT_SHA`. It is not the image entrypoint: an operator invokes it in a one-shot container using `--entrypoint /app/admin`, the candidate image, production `APP_ENV`/identity and the normal remote configuration permissions, and an operator-owned read-only password-file bind mount. Production `config.Load` clears `DATABASE_URL` and resolves the remote `DB_USER=mycfc_app`/`APP_DB_PASSWORD` pair to the stamped candidate's `mycfc_disposable_web_20261001` role. Do not attempt to bypass that with a local `DATABASE_URL` or connect as the old web principal or bootstrap superuser. Set `MYCFC_ADMIN_PASSWORD_FILE` to the in-container file. The file and its parent directory must be readable/traversable by the container's unprivileged UID; use a protected mount, not image layers, build args, a password flag, a password environment value, or an echo into a Compose log. Keep the service/traffic stopped until credentials and adult role are verified. SRE owns the exact one-shot host invocation/network/secret custody; this branch does not add a Compose service or host secret file.
- The owner/operator must supply an actual administrator name, email, date of birth and password via that image's existing `admin create --email ... --name ... --date-of-birth YYYY-MM-DD` CLI and `MYCFC_ADMIN_PASSWORD_FILE` (or its interactive terminal input when a real TTY is present). Do not put these in shell history, source, chat or logs. Verify that the resulting active adult ADMIN can authenticate and reach an authorized page before any route switch. The app does not invent an identity/password or turn a synthetically created test account into a production custodian. This is a separate custody decision, not a reason to omit the tested app path.
- The owner has separately authorized losing historical production member/event/training/publication records by a production DB delete/recreate; that operation has NOT happened here. Uploads and unrelated infrastructure remain untouched. SRE owns the exact host Compose/env compatibility and release sequence, including maintenance routing, backup/restore decision, and no-old-binary fallback. No live DDL, database reset, secret inspection, publication, merge or deployment occurs from this branch.

Real local evidence: `python3 scripts/test-fresh-database-release.py` starts disposable PostgreSQL 16.9, initializes the stamped candidate against empty `mycfc`, checks 77 ledger markers and digest `41eca3f0ca37f6e6ba5279fe1d931ff589de72b2a8586a77e31445e8a8b29ed7`, and verifies four login roles. It builds the actual stamped production image, runs `/app/admin` with `APP_ENV=production`, simulated production SSM/Secrets Manager responses containing an old `DB_USER`, and a deliberately privileged `DATABASE_URL` that production must clear. A synthetic adult ADMIN is created using the resolved candidate role and password file; mismatched candidate and missing password-file setting refuse, and the real login handler accepts only the correct password. Missing fresh-init flag/maintenance credentials, nonempty table/function, predecessor-bound `bootstrap-db` on empty, repeat init, tampered ledger, and migration-role-owned forged receipt also refuse. These are local disposable tests, not production acceptance.
