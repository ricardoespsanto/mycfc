# Implementation status

This document records the current implementation boundary. Planned and deferred work is tracked in the [MyCFC Delivery Project](https://github.com/users/ricardoespsanto/projects/1).

The #110 privacy-request workflow is implemented behind `PRIVACY_REQUESTS_ENABLED=false`: recently authenticated adults can submit and track requests, guardians receive a redacted receipt until case-specific representation is verified, and explicitly granted independent reviewers can claim, verify, extend, partially approve, refuse or approve cases with optimistic concurrency and immutable policy snapshots. #243 adds a closed, versioned execution-profile and category-purpose registry and server-compiled per-category plans containing concrete operation/field codes, owner, ground, an exact decision-anchored execution deadline, allowlisted retention anchors/calendar-day offsets, exact review/expiry timestamps only when the anchor exists at decision time, and a fail-closed fallback. Each plan is inserted atomically with the decision, stored separately from identifiable working data, made immutable, and assigned a request-bound server-computed SHA-256 digest that is recomputed on read until evidence expiry. #244 adds the disabled execution-control plane: an explicit executor grant independent of reviewer/admin authority; four-eyes start authorization; transactional revalidation of identity, representation, dependants and the last usable administrator; complete immutable job/checkpoint materialisation before `PROCESSING`; indexed session and token invalidation plus access/grant cutoff only for account closure; generic processing-start notification; fenced leases, attempts, retries and metadata-only failure evidence; and a distinct least-privilege database role. #245 adds the production-inactive relational execution foundation: a mechanically checked user-reference inventory, erased-account tombstones, subject-attachment guards, ordered lease-fenced database operations, atomic postcondition verification, a narrow immutable-prescription deletion path, and non-linking membership-history pseudonymisation after current/future participation is revoked. Explicitly implemented deletion, identity-clearing, repair-reporter and membership operations are executable. Audit pseudonymisation has fenced eight-table groundwork with recursive canary scrubbing and pseudonymous read labels, but remains outside the production allowlist until every intended provenance reference is covered; retained/expiring records, cross-store work, completion and activation also remain fail closed for later tickets. #246 now includes a production-inactive cross-store foundation: uploads no longer add user/request identifiers to object metadata; object keys are excluded from cleanup logs and equipment audit snapshots (including a forward migration for existing snapshots); a separate exact-key S3 implementation permanently enumerates and deletes all versions and delete markers with pagination, bounded passes, concurrent-change refusal, and two authoritative absence checks; an inert, deny-by-default protected database schema defines immutable object-target envelopes, rotation-aware keyed dedupe aliases and privacy-safe absence evidence, plus a separate append-only upload-intent/provenance journal with nullable source bindings for rolling-deploy compatibility; and distinct seal-only X25519/HKDF/AES-GCM upload and execution protectors keep worker private keys out of the web service. When the optional upload public/digest keys are configured, every new profile, repair and equipment photo reserves a protected intent before PUT and atomically attaches it to the pointer; failed, ambiguous, superseded and removed writes enter fenced cleanup, while expired unheld intents become stale after 24 hours. The least-privilege cleanup API decrypts only inside the separately configured worker, permanently deletes exact-key versions and markers, and records `ABSENCE_VERIFIED` only with stable authoritative listing evidence. Missing or partial upload-key configuration fails photo writes closed, and no cleanup worker, private key, live IAM or schedule is provisioned. The shared source lock/hold contract exists for future target capture, but execution-start target materialisation is not yet connected, so the full upload-versus-erasure race criterion is not claimed. Legacy purge or verified backfill, object-target materialisation, retained-object rewriting, factual provider registrations/adapters, key/service provisioning, permission activation and any live purge remain blocked. The immutable v1 plan remains fail closed for object deletion pending a new executor/schema/policy contract. Category-only requests preserve account access, unsupported plans fail before access cutoff, changed facts fail closed, and legacy unindexed sessions block account cutoff. The identifiable working-record period is approved at 90 calendar days after closure. Consent, core-identity, participation/history actions and internal periods, technical retention, backup/restore and external-provider governance have also been approved locally. Actual provider contracts/settings and external federation, insurance, accident, fiscal/payment, liability and health-basis facts remain unresolved.

The #246 provider/recipient slice now has a production-inactive, closed registry and protected transactional capture contract. Active generic provider rows are fenced against sync, webhook, credential refresh and reconnect before account cutoff; the exact target and minimum credential are sealed separately against the immutable execution binding; registry, target, credential and structured outcome evidence use distinct rotation-aware keyed digests; and a lease-fenced worker supports bounded retry, already-disconnected idempotency, and allowlisted `NOT_CONTROLLABLE` evidence only for registered autonomous recipients. The shipped registry is empty, inactive wearable integrations are explicitly outside its inventory, and unknown or insufficiently evidenced connections roll back capture. Factual #109 registrations, provider-specific source adapters, key/identity provisioning and activation remain blocked.

#247 completes the source-only retention and restore residuals without activating them: consent supersession, withdrawal, processing cessation and erasure establish an immutable three-year evidence expiry while IP/user-agent data retain the independent 12-month ceiling; eight inventoried audit families are pseudonymised per row at 24 months; and tracked repair photos enter existing exact-version cleanup at day 23 with authoritative absence required before day 30. One bounded retention API is exposed only through a fixed `NOLOGIN` capability role. Current closure-v4 tombstones separately authenticate the original erasure/consent effective time, the later closure-based evidence expiry, and a complete non-identifying membership-history postcondition digest and bounded row counts. Offline replay is database-only, locally fences restored provider credentials and reconnect/sync/webhook capability, independently recognizes and proves an exact source erasure already present in a newer backup, verifies retained historical memberships and variation payloads, and records immutable `ALREADY_APPLIED` evidence without mutation. A cryptographically marked synthetic fixture can exercise the same replay and attestation path in an isolated non-production restore but cannot represent a live subject. The candidate result and a dedicated table-blind observer aggregate are cross-bound to exact inventory, schema, policy, executor, plan, image and postcondition values; v1 and closure-v2/v3 evidence cannot cross the current replay boundary or authorize activation. Separate fail-closed CLIs and disabled timers emit only aggregate evidence through the existing CloudWatch path. Live database membership, credential provisioning, Terraform apply, timer activation, purge, promotion-gate enablement and deployment remain separate gates.

#248 adds a disabled-by-default privacy worker runtime and evidence recorder without activating production. A distinct executor database identity is restricted to fenced worker/readiness/status/completion routines; the hardened service rechecks database-clock readiness before every bounded cycle and destructive object batch, heartbeats active leases, stops on lost/expired activation, processes relational/object/tombstone work, recovers idempotent completion, and leaves the empty provider registry fail closed. Exact media-version deletion, restore-ledger invocation, write-only CloudWatch logs, and terminal/aged/missing-heartbeat alarms remain separate Terraform gates. Activation requires a current independently observed HMAC-authenticated restore attestation plus Ed25519-signed infrastructure/provider-ready/schema artifacts no older than 90 days, with exact immutable image/schema/state/plan/version bindings and distinct executor proposal plus administrator approval. This release’s empty provider registry emits only `NOT_READY`, so no provider fact, credential, Terraform apply, feature flag, live deletion, activation, or purge is supplied by the source change.

For the configured #246 upload path specifically, a protected locator commitment, exact content/size checks and a deferred commit-time invariant prevent an intent from being attached without its matching pointer. Cleanup claims recheck that the exact source no longer references the intent. Legacy pointers remain readable, but replacement and removal are blocked until the separately approved purge or verified backfill can retain cleanup provenance.

The Hoje view includes a club distance leaderboard for the current week, month, year, or all recorded time. It ranks only distances attached to completed training sessions, handles tied positions, shows the first ten positions plus the signed-in athlete when applicable, and excludes future sessions, inactive memberships, and private accounts. Athletes control their own leaderboard visibility; guardians control it for their dependants.

Wearable activity providers share an extensible adapter contract for connection status, bounded recent sync, backfill, webhook ingestion, and disconnection. Provider names and remote identifiers are not closed database enums, so Polar, Garmin, Strava, WHOOP, and later providers can use the same persistence model. No provider-specific OAuth, external API call, visible integration UI, automatic activity matching, or login-triggered sync is part of this foundation.

Training plans and sessions are scoped to teams or programmes, with teams preferred as the existing group model. Sessions are visible from active matching memberships without individual assignment. The structured-planning foundation, guarded by the `structured_training_planning` feature flag and administrator-only by default, reuses those durable plan/session identities while adding training groups, dated weeks with an explicit persisted season, rest/competition/logistics entries, ordered hybrid segments (including gym, water, run, bike, ergometer, mobility, and games), and ordered warm-up/main/cool-down/technique blocks. Management users can organize those independent weekly drafts into optional, hierarchy-capable multi-week cycles with free-text level, goals and phase/focus notes, ordered weeks, and competition targets. Cycle cards report every week's planned-load percentage and modality mix, explicitly warn when either is missing, and link back to the weekly editor. Optimistic concurrency protects cycle edits. Copying a cycle deep-copies its weeks and structured sessions into independent drafts while deliberately leaving publications, athlete outcomes, and competition targets behind. Structured water segments add continuous, interval, fartlek, technique, starts, race-simulation, technical/tactical and custom methods; nested repeat groups with recovery at the prescribed level; mixed exact or estimated duration/distance efforts; cadence and readable kayak-polo drill metadata; free text; and a session-distance target suitable for “continue until 12 km” cooldowns. Planned effort, recovery, distance, and time-by-intensity totals are derived without inventing pace and are labelled exact, estimated, or unknown. Administrators manage club-defined, revisioned kayak/canoe intensity profiles and zones; new revisions copy the previous zones, historical blocks retain their selected revision, R7 remains duration-relative, and no disputed R5 default is seeded. Structured gym segments add straight sets, circuits and supersets; repeated rounds and recovery; ordered exercise prescriptions; resistance through kg, %1RM, body weight, band, RPE, RIR or coach instruction; execution intent and tempo; and optional hybrid start offsets, transition time and equipment notes. Session modality summaries are derived from their ordered segments. Coaches can save immutable block, segment or session snapshots as private routines or share them only within the source plan's authorized programme/team scope; the library supports modality, objective, method, tag and text filtering with a readable preview. Routine insertion and direct block, session, day or full-week copying reconstruct independent relational drafts—including water prescriptions, nested steps, and profile revision—and append lightweight provenance, so later edits cannot rewrite the source. In-scope coaches can target bounded omit, replace, add, or field-override variations at an athlete, subgroup, or date-effective temporary crew; crew capacity follows the configured K2/K4/C2/C4-style craft code, individual rules outrank group rules, and same-priority matches block publication. Publication resolves one private, immutable snapshot per eligible athlete and session, with exact new/changed/removed/unchanged preview counts, optimistic source-version protection, append-only revision history, and outcome lineage fixed to the first recorded prescription revision. Athletes see only their published prescriptions; named guardians see only current minor dependants; administrators and currently in-scope coaches can inspect authorized history. Ordinary training cards, calendars, and programme agendas link to the current authorized prescription without embedding athlete identity in the URL. Historic revisions remain readable after later draft, membership, group, crew, profile, or intensity-zone changes. Completed-session feedback now stores athlete-reported actual duration and distance separately from the immutable prescription, plus optional 0–10 perceived effort, 1–5 overall feeling, and a bounded note. Corrections are version-checked and timestamped; the response remains attached only to the performed prescription revision. Current minor guardians and current in-scope coaches have read-only access, while unrelated users receive not-found. Wearable-derived planned/realized load remains a later ticket in the training epic. Administrators and in-scope coaches can edit active future sessions with optimistic concurrency; moving a session to another plan requires access to both plans and becomes locked after the first athlete outcome. They can also irreversibly cancel a future session with an actor, timestamp, and trimmed reason while preserving existing outcomes and replacement links. Cancelled sessions remain visible across athlete, staff, calendar, Hoje, and programme-agenda surfaces, reject outcome and distance changes, cannot be selected as new replacements, and do not contribute to the distance leaderboard. Athletes report `COMPLETED`, `MISSED`, or `REPLACED` outcomes; a replacement must identify another visible active session and a short reason. A completed outcome can store optional actual duration and distance plus the athlete's bounded perception; the athlete can later correct or remove those values while the session remains active and the submitted outcome version remains current. Staff attendance and check-in are not part of the training workflow.

Equipment inventory entries support administrator-uploaded JPEG, PNG, or WebP photos stored privately and displayed through short-lived signed URLs. Photo-bearing creates preallocate the equipment identity, configured writes bind protected provenance atomically, and replacements queue the prior intent for version-aware cleanup. Photo replacements remain represented in equipment audit history without storing object keys.

Authenticated person surfaces use the profile avatar endpoint for account context, guardian/dependant views, the administrator member directory, event responses/check-ins, and the distance leaderboard. The endpoint serves only a current-consent photo for an active member (or an inactive member to an administrator) and otherwise returns an initials image without exposing profile data.
