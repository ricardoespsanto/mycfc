## Persistence contract for #336–#339

- `user_memberships.id` is the stable historical reference. Each participation row belongs to one user, season and programme, with inclusive `starts_on`/`ends_on` dates. NULL ends are bounded by the season in the trigger on insertion. A GiST exclusion prohibits any overlapping day across **all** programmes for the same user. Closing and later reactivating the same programme inserts a *new* row/ID; never reopen or re-key a referenced interval. A repeated upsert on a day already covered returns that row unchanged. Concurrent inserts can fail `23P01`; the handler retries one concurrent winner read, then gives a validation error.
- `team_id` and `competition_category_id` belong to the same season/programme (composite foreign keys). `Competition` requires a category; `Leisure` and `Kayak_Polo` prohibit it. Initiation currently has no additional category rule. Category birth-date eligibility is checked against the user's DOB at the time of the write. Reasoned mismatches remain **DB-disabled** until an authenticated, scoped and audited exception service and manual privacy runbook are built; a caller-set PostgreSQL GUC is forgeable and cannot supply authority. The generated dated-insert API accepts no actor/time parameters.
- Current membership readers use inclusive dates (`starts_on <= CURRENT_DATE AND ends_on >= CURRENT_DATE`). #336–#339 must select the interval appropriate to the actual training/event/publication date and preserve the selected membership ID and immutable published snapshots, not recompute past assignments from current membership. This cutover rejects direct changes to classification identity/start, reopening a closed interval, referenced category birth-date definitions and DOB of a classified user. Shortening `ends_on` is rejected with a staff-facing explanation when it excludes a published prescription's actual membership ID and session date, a programme-audience or general event response date, or a recorded training outcome attached through the membership's group; published snapshots/hashes and recorded rows are not rewritten. Exceptional corrections remain blocked until an authorized audited/versioned service exists. Concurrent insertion of event/training associations versus a direct SQL end update still requires a coordinated workflow/review; this is not a complete history-correction service.
- The admin toggle is restricted to today-only ordinary assignments for non-competition programmes. The server-side `db.DatedParticipationService.CreateOrdinaryAssignment(ctx, OrdinaryDatedAssignment) (dbgen.UserMembership, error)` accepts an active adult administrator, eligible member, season, programme, optional competition category and a Lisbon date of today or tomorrow. `TransitionNextDay(ctx, oldMembershipID, OrdinaryDatedAssignment) (dbgen.UserMembership, error)` atomically closes an earlier-started interval today and inserts a new interval tomorrow; it verifies the actor and subject inside a serializable transaction and leaves the old ID/history intact on failure. The sqlc `CreateDatedParticipation` insertion is a lower-level unscoped query: route callers through this service, not directly to the query. PostgreSQL GiST exclusion rejects overlap; `EndCurrentSeasonMembership` requires an interval started before today, and the admin form explains why a same-day assignment cannot be ended. Ordinary API does not authorize backdates, reasons, reopenings or same-day transitions. The existing admin form still cannot create competition classifications (no escalão picker) or author exceptions. There is no staff-facing dated form for tomorrow's scheduled transition yet; #336/#338 can consume the service, not invent authorization from caller-supplied flags. Race with independently inserting associations remains an open release gate; do not claim #335 acceptance until that workflow and remaining current/published authorization cases have tests.

## Data-loss and cutover guardrails

The migration has no `DELETE`, `TRUNCATE`, table replacement or user/member reset. It fails closed when legacy membership rows have NULL ends, out-of-season dates or invalid category assignments. It neither silently alters their IDs nor deletes dependants. A non-member `news_items` row survived an isolated predecessor-schema migration test; this does **not** prove live data is empty or the whole durable state is covered. Before any destructive cleanup, inventory all non-member durable records and foreign keys. In particular, `news_items`, `seasons`, `programmes`, `modalities`, `competition_categories`, `teams`, `events`, `training_plans`, `training_sessions`, `training_plan_publications`, `training_prescriptions`, `equipment` and associated fleet/maintenance records may have durable meaning. Deleting `users` can cascade or be blocked by linked event responses, training/performance logs, teams, plans, immutable publications and prescriptions. Never infer that 'no real members' authorizes deleting these rows, a DB reset, changing historical event/training records, or republishing prescriptions. A live row-count/FK audit and human approval remain separate.
